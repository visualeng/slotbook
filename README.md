# slotbook

Сервис бронирования ресурсов: переговорок, машин, столов. Интервалы вместо
точечных слотов, защита от двойного брони на уровне базы и живое обновление
расписания в открытых вкладках.

[![Node](https://img.shields.io/badge/node-24-3c873a)](https://nodejs.org)
[![Postgres](https://img.shields.io/badge/postgres-17-336791)](https://www.postgresql.org)

## Что это за задача

Бронировать ресурсы «на час» недостаточно: люди занимают переговорку с 09:30 до
10:30, потом с 10:30 до 12:00, а кто-то пытается взять 10:00–11:00, когда там
уже сидят. Значит, домен — это интервалы, и главный вопрос один: **как сделать
так, чтобы два человека не заняли один и тот же слот**.

Ответ здесь такой: проверять это в приложении нельзя. Любая проверка «а не
занято ли» проигрывает гонке двух одновременных запросов — между `SELECT` и
`INSERT` вклинивается второй. Поэтому запрет живёт в самой базе, в виде
exclusion-ограничения, и не нарушается ни при какой нагрузке.

```sql
slot tsrange GENERATED ALWAYS AS (
          tsrange(day::timestamp + start_minute * interval '1 minute',
                  day::timestamp + end_minute * interval '1 minute')
      ) STORED,

CONSTRAINT bookings_no_overlap EXCLUDE USING gist (resource_id WITH =, slot WITH &&)
  WHERE (status = 'CONFIRMED'),
CONSTRAINT bookings_user_no_overlap EXCLUDE USING gist (user_id WITH =, slot WITH &&)
  WHERE (status = 'CONFIRMED')
```

Первое ограничение говорит «слот ресурса не пересекается с другим слотом этого
же ресурса», второе — «человек не может быть в двух местах одновременно». Частично
отменённые брони в проверке не участвуют, поэтому отмена освобождает время без
пересоздания сетки. Тест на десять параллельных запросов к одному слоту —
в репозитории, в `tests/integration/concurrency.test.ts`.

## Стек

| Слой | Чем и почему |
| --- | --- |
| Язык | TypeScript 7 (native-компилятор), `strict` без единого `any` |
| Сервер | Fastify 5 — быстрый, с нормальным `inject()` для тестов |
| База | PostgreSQL 17, сырой SQL без ORM: запросы тут короткие и читаемые |
| Схема | миграции из `db/migrations`, накатываются при старте |
| Клиент | React 19 + Vite 8, общие типы с сервером |
| Live | Server-Sent Events — данных мало, WebSocket был бы дороже |
| Тесты | Vitest 5 (юнит, интеграционные, компоненты) + Playwright (e2e) |
| Линт | Biome 2 — формат и правила в одном инструменте |
| CI | GitHub Actions: матрица Node 22/24, интеграционные с Postgres, e2e, сборка образа |

## Быстрый старт

Всё вместе, одной командой:

```bash
docker compose up --build
# интерфейс: http://localhost:3000
```

Без Docker (нужны Node 22+ и Postgres 17+):

```bash
cp .env.example .env          # подставить свой пароль
createdb slotbook
npm install
npm run dev                   # API на :3000
npm run dev:web               # интерфейс на :5173 с прокси на API
```

Миграции применяются при старте сервера, отдельной командой их запускать не
нужно.

### Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | `postgres://host:port/db` — **без логина и пароля** |
| `DATABASE_USER`, `DATABASE_PASSWORD` | логин и пароль отдельными полями |
| `PORT` | порт HTTP-сервера, по умолчанию 3000 |
| `WEB_DIST`, `MIGRATIONS_DIR` | где собранный веб и где миграции |
| `TEST_DATABASE_URL` | база для интеграционных тестов; без неё они молча пропускаются |

Логин и пароль вынесены из DSN намеренно: одна и та же строка подключения должна
работать в разных окружениях, а секреты не должны попадать в URL, который
кто-то выведет в лог.

## API

Все ответы — JSON, ошибки всегда с кодом и сообщением на русском:
`{ "code": "slot_taken", "message": "слот уже занят", "details": { "conflicts": [...] } }`.

```bash
# что бронируем
curl -s localhost:3000/api/resources
# → [{ "id": "1111…", "name": "Переговорная «Кофе»", "slotMinutes": 30, "openMinute": 540, "closeMinute": 1080 }]

# сетка слотов на день с точки зрения пользователя alice
curl -s "localhost:3000/api/resources/1111.../schedule?day=2026-09-28&viewer=alice"
# → { "slots": [ { "startMinute": 540, "endMinute": 570, "state": "FREE", "booking": null }, … ] }
# state: FREE — свободно, BOOKED — занял кто-то другой, MINE — моя бронь

# забронировать 09:00–10:00
curl -s -X POST localhost:3000/api/bookings -H 'content-type: application/json' -d '{
  "resourceId": "11111111-1111-4111-8111-111111111111",
  "userId": "alice", "day": "2026-09-28",
  "startMinute": 540, "endMinute": 600, "title": "ревью архитектуры"
}'
# → 201 с созданной бронью

# тот же слот другому человеку → 409 slot_taken, в details.conflicts видно чужую бронь
# начало не по границе слота → 400 not_aligned
# за пределами рабочего дня → 400 outside_hours
# отменить → 200, слот снова свободен
curl -s -X DELETE "localhost:3000/api/bookings/<id>?userId=alice"

# список броней дня
curl -s "localhost:3000/api/bookings?day=2026-09-28&userId=alice"

# поток событий: booking.created и booking.cancelled
curl -N localhost:3000/api/stream
```

Время везде — целым числом минут от полуночи (`540` = 09:00), день — строкой
`YYYY-MM-DD`. Ни таймзон, ни локаль не участвуют в сравнениях, поэтому бронь
09:00 в 09:00 и в Казани, и в Берлине.

## Устройство

```
db/migrations/001_init.sql   схема, ограничения и три демо-ресурса
src/shared/types.ts          типы, которые знают и сервер, и браузер
src/server/
  index.ts                   конфиг, база, миграции, HTTP
  app.ts                     сборка приложения и единый формат ошибок
  db.ts                      пул и применение миграций
  config.ts                  разбор переменных окружения
  events.ts                  шина событий для /api/stream
  domain/slots.ts            сетка слотов и проверки границ — без базы и HTTP
  domain/booking-service.ts  всё, что ходит в базу
  routes/                    resources.ts, bookings.ts, stream.ts
src/web/                     React: App.tsx, api.ts, components/, hooks/useStream.ts
tests/unit/                  чистая логика: сетка, интервалы, шина событий
tests/integration/           API и гонки на настоящем Postgres
tests/web/                   компоненты и страница целиком с подменённым fetch
e2e/                         Playwright: три сценария в браузере
```

Правила предметной области (сетка слотов, кратность интервала, попадание в
рабочие часы) живут в `domain/slots.ts` и проверяются обычными юнит-тестами —
там нет ни базы, ни HTTP. Всё, что ходит в базу, — в `BookingService`; нарушение
ограничения превращается в `409` с понятным описанием конфликта, а не в `500`.

## Тесты

```bash
npm test                # всё: 58 тест
npm run test:unit       # логика без базы
npm run test:web        # компоненты и страница (jsdom)
npm run test:integration  # нужна TEST_DATABASE_URL
npm run e2e             # Playwright, поднимает собранное приложение сам
npm run lint && npm run typecheck
```

Интеграционные тесты запускаются последовательно (`--no-file-parallelism`): они
делят одну базу и чистят её перед каждым тестом, параллельный прогон означал бы,
что файлы мешают друг другу. Без `TEST_DATABASE_URL` они не падают, а
пропускаются — так их можно запускать на машине без базы, а в CI (с сервисом
Postgres) они уже обязательные.

Что покрыто и почему именно это:

- **юнит** — сетка слотов, пересечение полуоткрытых интервалов, проверки границ,
  формат даты, поведение шины событий при упавшем подписчике;
- **интеграционные** — весь API через `inject()`: коды ошибок, содержимое
  `details` при конфликте, фильтры, отмена и освобождение слота;
- **гонки** — десять параллельных заявок на один слот, два параллельных запроса
  от одного человека, гонка брони с отменой, заполнение дня целиком;
- **компоненты** — сетка, панель выбора, список своих броней;
- **клиент** — заголовки и разбор ошибок: `DELETE` отправляется без тела, иначе
  fastify отвечает 400 «Body cannot be empty»; интеграционные тесты через
  `inject()` этот случай не видели, поймал его e2e;
- **страница целиком** — с подменёнными `fetch` и `EventSource`: два клика
  собирают диапазон, событие из потока перезапрашивает расписание;
- **e2e** — бронь и отмена в браузере, запрет диапазона через занятый слот и
  обновление чужой вкладки без перезагрузки.

## Решения и компромиссы

**Exclusion-ограничение вместо блокировок.** `SELECT … FOR UPDATE` в проекте
вроде orderflow тоже работает, но там объекты конфликта известны заранее. Здесь
конфликт — это пересечение интервалов, которое нельзя выразить уникальным
индексом, а вычислять «занятые интервалы» в приложении — значит снова иметь
гонку. `btree_gist` + `tsrange` решают задачу на уровне данных, и это стоит
одной строки в схеме.

**Конфликты различают по имени ограничения.** Когда `INSERT` падает, в ошибке
есть `err.constraint` — видно, какое именно правило нарушено. Поэтому «слот
занят» и «ты уже в другом месте» получают разные коды и разные подсказки с
чужими бронями, а не один общий `409`.

**SSE вместо WebSocket.** Событий мало, они идут в одну сторону, переподключение
и ретраи браузер делает сам. Код потока — 40 строк вместо отдельной библиотеки с
протоколом.

**`userId` приходит из запроса, аутентификации нет.** Это осознанное упрощение
стенда: без входа в систему «мои брони» определяется полем, которое можно
подделать. В боевом сервисе здесь был бы `session` из middleware, а поле в
таблице осталось бы прежним.

**Сырой SQL вместо ORM.** Запросов пять, три из них — это `SELECT` с джойном и
параметрами. ORM здесь добавила бы слой, который всё равно пришлось бы обходить
ради `EXCLUDE`, а её версии и так тянут за собой миграции отдельным инструментом.

**Миграции накатываются при старте.** Отдельного шага в деплое нет: миграций
три, они идемпотентны и применяются в транзакции. Пока их столько, скользящий
деплой с отдельным шагом миграций придумывать рано.

**Сервер собирает esbuild, типы проверяет tsc.** TypeScript 7 больше не
умеет собирать CommonJS, а он удобен тем, что не нужно расставлять `.js` в
импортах. Собирает esbuild, проверяет типы `tsc --noEmit`, проверок две — обе
в CI.

**Веб отдаёт тот же процесс, что и API.** В проде это один контейнер: статика
лежит рядом, отдельный nginx не нужен. В разработке интерфейс живёт на Vite с
прокси на API.

## Чего пока нет

- [ ] аутентификации: `userId` приходит из запроса, см. выше;
- [ ] переноса брони на другой день и повторяющихся событий (RRULE);
- [ ] уведомлений по email при освобождении слота;
- [ ] постраничной выдачи расписания на месяц — сейчас сетка строится на день;
- [ ] метрик и structured-логов в формате, пригодном для агрегации;
- [ ] нагрузочного теста: `k6` сценарий «утро понедельника, все бронируют
  девятичасовую переговорку» — следующий шаг, профиль уже придуман.
